# Contrôle sauvegarde et reprise — 2026-10-12

## Résultat local

Le périmètre de sauvegarde vérifiable localement est **conforme** à `conventions/backup.md` : une
archive de test contenant uniquement des données synthétiques est chiffrée, vérifiée après
déchiffrement, restaurée dans une nouvelle base et purgée selon la rétention. La copie indépendante
hors hôte et les opérations sur l'hôte de production sont exclues du statut local et restent dans
`TODO.md`. Aucun volume ni hôte de production n'a été utilisé.

| Vérification | Preuve exécutée | Résultat |
|---|---|---|
| Build image de sauvegarde | `docker build --pull -t erp-rh-backup:backup-control ./backup` | Image construite avec `age` 1.3.2, PostgreSQL 18.6 et outils de dump/restore |
| Syntaxe des scripts | `sh -n /usr/local/bin/backup-postgres` et `sh -n /usr/local/bin/backup-scheduler` dans l'image | Réussi |
| Obligations de configuration | `docker compose --env-file .env.example config --quiet` ; puis variable `BACKUP_AGE_RECIPIENT` vide | Configuration valide ; absence de clé rejetée explicitement |
| Validation du destinataire | Planificateur exécuté avec `change-me-age-recipient` | Arrêt immédiat avec erreur explicite ; aucun dump lancé |
| Chiffrement et production | Base PG18.6 jetable ; table `backup_probe`, une ligne synthétique et rôle `backup_probe_user` ; exécution de `backup-postgres` | Archive `.tar.gz.age` créée en mode `0600` ; contrôle `pg_restore --list`, lecture tar et sommes SHA-256 réussis avant chiffrement |
| Accès à l'archive | Identité age synthétique dans un volume jetable ; déchiffrement et extraction | `globals.sql: OK`, `database.dump: OK`, `pg_restore --list` réussi |
| Restauration isolée | Rôles restaurés dans une base PG18 vide, puis restauration du dump custom | La ligne `local-backup-control` et le rôle `backup_probe_user` sont retrouvés dans la cible neuve |
| Rétention | Fichier synthétique daté de 31 jours, rétention à 30 jours, second backup | Ancienne archive supprimée ; seules les archives récentes `.tar.gz.age` restent |
| Planification | Service temporaire démarré avec une archive récente et `BACKUP_TIME_UTC=02:00` | Journal : prochaine exécution `2026-10-13 02:00:00 UTC` |
| Santé du service | Healthcheck Compose | Exige PostgreSQL disponible, répertoire inscriptible et archive chiffrée de moins de 24 heures |

Le dossier temporaire contenant le tar en clair est créé sous `/tmp` et supprimé au succès ou à
l'échec ; Compose monte `/tmp` en tmpfs. Le seul fichier qui reste dans `./backups/` est donc
l'archive `.age`, avec des permissions restreintes. Après le contrôle, la clé privée de l'exercice,
les deux conteneurs, le conteneur planificateur, le réseau et les volumes jetables ont été supprimés.

## Objectifs de reprise

- **RPO cible : 24 heures** — sauvegarde quotidienne à `02:00 UTC`, avec nouvelle tentative horaire
  après un échec. Le healthcheck devient unhealthy si aucune archive chiffrée récente n'est disponible.
- **RTO cible : 4 heures** — cible choisie par le propriétaire le 2026-10-12. L'exercice synthétique
  de déchiffrement et restauration a abouti dans ce délai ; la validation au volume de données réel
  reste une opération serveur.
- **Rétention : 30 jours**, selon les variables de configuration actuelles.

## Utilisation de la clé

Sur le poste d'administration, `age-keygen` produit une clé privée et affiche la clé publique. Seule
la clé publique va dans `BACKUP_AGE_RECIPIENT` du `.env` de production. La clé privée reste hors du
serveur et doit avoir une copie de secours protégée ; elle est indispensable pour déchiffrer. Les
commandes d'installation, de création de clé, de déchiffrement et de restauration sont dans
[`deployment.md`](../deployment.md#preparer-la-cle-age-et-acceder-aux-archives).
